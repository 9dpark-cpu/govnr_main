2.0 EXECUTIVE SUMMARY
This volume details the physical and logical cloud architecture of Govnr Systems Inc. The infrastructure is designed to achieve three conflicting objectives simultaneously: absolute security (zero-liability data handling), frictionless enterprise onboarding (bypassing legacy IT firewalls), and ruthless cost-efficiency (leveraging PaaS and IaaS interoperability without over-provisioning).

2.1 OVERARCHING TOPOLOGY & DIGITALOCEAN APPARATUS
The Govnr infrastructure is hosted entirely within DigitalOcean, utilizing a hybrid deployment of Platform-as-a-Service (PaaS), Infrastructure-as-a-Service (IaaS), and Managed Databases.

A. Govnr-Core (Web Service): A DigitalOcean App Platform container running the Streamlit frontend. It operates continuously to serve the CFO Executive Dashboard and the administrative configuration interfaces. It is sized efficiently (e.g., 512MB to 1GB RAM) as Polars data manipulations for the UI are optimized.
B. Govnr-Outbound-Worker (Scheduled Job): A completely isolated, headless container deployed from the identical GitHub codebase. It is triggered via a standard Cron expression (`15 10 * * *` for 10:15 UTC / 6:15 AM EDT). It wakes up, executes the financial calculus, dispatches SMTP emails, and terminates. It is billed precisely for the seconds it runs (averaging <$5.00/month).
C. Managed PostgreSQL: A dedicated, isolated database cluster handling configurations, intraday state locking, and the anonymized proprietary data vault.
D. The SFTP Drop Zone: A standalone $4/month Ubuntu Droplet (IaaS) operating exclusively as a secure file reception buffer between the client's ERP and the Govnr engine.

2.2 THE SFTP DROP ZONE & NETWORK CAMOUFLAGE
Integrating with on-premise or legacy Enterprise Resource Planning (ERP) systems (e.g., Epicor, older NetSuite builds) via native APIs is financially and operationally prohibitive. Govnr bypasses these paywalls and IT blockers via secure SFTP batch file transfers.

A. The Port 443 Egress Bypass: Traditional corporate IT environments restrict outbound traffic on non-standard ports, frequently blocking Port 22 (Standard SSH/SFTP). To guarantee seamless data delivery without requiring custom firewall exceptions from the client’s IT department, the Govnr SFTP Droplet listens on Port 443. This provides HTTPS camouflage, ensuring the ERP's outbound CSV push is treated as standard secure web traffic.
B. Private VPC Routing: DigitalOcean App Platform containers have dynamic, rotating outbound IP addresses. Securing a Dedicated Egress IP costs $25/month. To bypass this, the Govnr Scheduled Worker connects to the SFTP Droplet exclusively via DigitalOcean’s internal Virtual Private Cloud (VPC) on a 10.x.x.x private network. This ensures data transit remains off the public internet, maximizing security while minimizing operational expense.
C. Client Isolation (Chroot Jails): The SFTP Droplet is configured with strict `ChrootDirectory` jails. Each client (`client_test_001`) is cryptographically locked into their specific `/inbound` directory. Cross-tenant visibility is physically impossible at the OS level.

2.3 SECRETS MANAGEMENT & ENVIRONMENT VARIABLES
No credentials, database strings, or cryptographic keys are permitted in the GitHub repository.

A. App-Level Encryption: All infrastructure relies on DigitalOcean App-Level Environment Variables. Variables such as `DATABASE_URL`, `SMTP_PASS` (the 16-character Google Workspace App Password), and client-specific SFTP passwords (e.g., `CLIENT_TEST_001_SFTP_PASSWORD`) are injected securely at runtime and encrypted at rest.
B. Dynamic Credential Resolution: The headless Cron Worker does not hardcode client IPs or credentials. It queries the `client_ingestion_config` PostgreSQL table to resolve the dynamic environment variable string assigned to each client, allowing a single worker to securely parse hundreds of discrete SFTP nodes asynchronously.

2.4 EPHEMERAL CONTAINER LOGIC
Govnr adheres to a strictly stateless compute architecture. The DigitalOcean App Platform containers possess no persistent storage.

A. In-Memory Execution: When the `govnr-outbound-worker` executes, it pulls the target CSV files from the SFTP Drop Zone into the container's temporary disk space. The Polars engine loads the data entirely into RAM, computes the financial calculus, generates the PDF/CSV byte buffers, and dispatches the payload via SMTP.
B. Stateless Resilience: Because the container is destroyed and rebuilt routinely by DigitalOcean, local directory drift or accumulated log bloat is physically impossible. This guarantees that each 6:15 AM execution occurs in a mathematically sterile environment.

2.5 SOC2 DATA DESTRUCTION MANDATE (THE ZERO-LIABILITY PROTOCOL)
Protecting client pricing data, vendor lists, and proprietary SKUs is the highest architectural priority. Govnr reduces its legal liability to zero by ensuring no raw client data survives the computational session.

A. Local Ephemeral Destruction: Embedded within the `daily_cron_job.py` script is a strict `try/finally` execution block. Regardless of whether the math engine succeeds, throws a `ComputeError`, or fails an SMTP relay, the `finally` block executes `shutil.rmtree()` on the client's nested `/inbound/<client_uuid>` directory, and `os.remove()` on the canonical root files. The ephemeral disk is shredded immediately.
B. Remote SFTP Pruning: By default, client CSVs accumulate on the SFTP Droplet. During the initial 14-day POV, these files are retained to permit manual forensic debugging of NetSuite anomalies. Once stability is proven, the `delete_remote_after_success` boolean is toggled to True in the Streamlit UI. 
C. The Cleanup Execution: When `delete_remote_after_success = True`, the Cron Worker establishes a secondary Paramiko connection post-email-delivery and executes `sftp.remove(remote_path)` on the specific tracked files. This sanitizes the SFTP Droplet daily, ensuring zero storage bloat and negating the risk of mass data exfiltration in the event of an IaaS breach.

3.0 EXECUTIVE SUMMARY
This volume defines the PostgreSQL state management architecture. Govnr’s database is not a raw data warehouse; it is a highly sanitized, relational state manager. 3.1 CORE ENTITY SCHEMAS (CONFIGURATION & ACCESS)
The foundational relational tables govern client identity, system access, and the automated pipeline instructions.

A. The `clients` Table:
Serves as the root entity for foreign key relations. It holds static, non-operational data.
- Fields: `client_uuid` (UUID, Primary Key), `company_name` (VARCHAR), `contact_email` (VARCHAR), `account_tier` (VARCHAR).
- Security: The `client_uuid` is the absolute primary key used across the entire backend infrastructure for directory creation and data routing. 

B. The `client_ingestion_config` Table:
Acts as the central command configuration for the automated cron worker. It dictates where the worker goes, how it authenticates, and how it translates the data.
- SFTP Routing Fields: `sftp_host`, `sftp_port`, `sftp_username`, `sftp_inbound_path`.
- Credential Resolvers: `sftp_password_env_var`, `sftp_private_key_env_var`. (These instruct the worker on which DigitalOcean App-Level Environment Variable contains the decrypted password for this specific node).
- Pattern Matchers: `inventory_filename_pattern`, `annual_sold_filename_pattern`, `po_filename_pattern`.
- Operational Rules: `weekly_otb_limit` (Float), `delete_remote_after_success` (Boolean).
- The Rosetta Stone Mappings: `inventory_column_mapping`, `annual_sold_column_mapping`, `po_column_mapping` (Stored as JSONB dictionaries).

3.2 THE FINANCIAL LEDGER (`client_metrics_history`)
This table is the state provider for the Streamlit Executive Dashboard. It stores the finalized mathematical outputs computed by the Polars engine.
- Schema Fields: `date_recorded` (DATE), `total_capital_deployed` (NUMERIC), `inventory_turnover` (NUMERIC), `gross_margin_pct` (NUMERIC), `avg_gmroi` (NUMERIC), `dead_stock_val` (NUMERIC), `rolling_po_exposure` (NUMERIC), `weekly_otb_limit` (NUMERIC).
- The Singularity Constraint: The table strictly enforces `UNIQUE(client_uuid, date_recorded)`. This constraint is structurally mandatory to prevent duplicate row generation on the frontend line charts, which would otherwise cause the Executive Dashboard to crash or render distorted zig-zag visualizations.

3.3 INTRADAY STATE LOCKING (THE UPSERT OVERRIDE)
A critical business reality is that the financial state is volatile intraday. The automated cron worker runs at 6:15 AM, recording $0 in Draft PO exposure. At 2:00 PM, a buyer drafts a $150,000 freight order. When the CFO clicks "Manual Execution" at 2:05 PM, the database must reflect the new reality.

A. The Conflict Resolution: To comply with the `UNIQUE` daily constraint while accepting new intraday data, `auth.save_cfo_metrics()` utilizes a strict `UPSERT` execution.
B. The SQL Execution:
   `INSERT INTO client_metrics_history (...) VALUES (...)`
   `ON CONFLICT (client_uuid, date_recorded) DO UPDATE SET`
   `total_capital_deployed = EXCLUDED.total_capital_deployed,`
   `inventory_turnover = EXCLUDED.inventory_turnover,`
   `dead_stock_val = EXCLUDED.dead_stock_val,`
   `rolling_po_exposure = EXCLUDED.rolling_po_exposure,`
   `weekly_otb_limit = EXCLUDED.weekly_otb_limit;`
C. State Preservation: This command explicitly overwrites the existing metrics for the current day with the absolute newest snapshot generated by the Polars engine, ensuring the CFO Dashboard always displays mathematically accurate Cash Collision warnings.

3.4 THE IP HARVESTER & DEMAND RADAR VAULT
The enterprise exit valuation ($1B+) is predicated on the aggregation of macroeconomic supply chain data across 1,500+ independent nodes. This data is extracted and stored in the `demand_radar_vault`.

A. Anonymization Protocol: Proprietary client pricing, specific vendor lists, and explicit PO data are strictly prohibited from entering the vault. 
B. Categorical Aggregation: The `ip_harvester.py` script maps raw SKU descriptions to standardized macro-categories (e.g., "Brakes & Rotors", "Alternators"). It groups this data by region (derived from the client node).
C. Vault Schema: `date_recorded`, `client_hash` (A one-way cryptographic hash of the `client_uuid` to break traceability), `region`, `part_category`, `regional_stock_count`, `regional_velocity`, `regional_capital_deployed`, `regional_surplus_deficit`.

3.5 ARCHITECTURAL GUARDRAILS (THE HARVESTER BUG)
During the QA phase, a severe state-corruption bug was identified and permanently neutralized. Any future modifications to the database schema must respect this sequence:
- The Chronological Rule: `ip_harvester.py` MUST run strictly *after* `auth.save_cfo_metrics()`. 
- The Overwrite Ban: `ip_harvester.py` calculates its own internal variables to determine regional capital. Previously, it contained an `UPSERT` command that overwrote `dead_stock_val` in the `client_metrics_history` table using a lazy, global zero-sales calculation ($128k), corrupting the strict Location-First calculus ($56k) saved by the main engine.
- The Law: The harvester script is permanently banned from modifying `dead_stock_val`, `rolling_po_exposure`, or `weekly_otb_limit` in the `client_metrics_history` table. Its sole domain is the `demand_radar_vault`.

4.0 EXECUTIVE SUMMARY
This volume defines the data ingestion pipelines and parsing constraints of the Govnr engine. Legacy Enterprise Resource Planning (ERP) data is inherently contaminated, prone to formatting inconsistencies, type collisions, and missing variables. The parsing layer acts as a ruthless quarantine filter. Utilizing the Polars data-frame library, Govnr enforces strict schema casting, relational key validation, and pre-flight mapping checks to guarantee that no mathematically corrupted data ever enters the core financial calculus engine.

4.1 THE 3-FILE INGESTION ARCHITECTURE
The Govnr architecture relies on three explicit, flat CSV files exported dynamically from the client's ERP (NetSuite, Epicor, etc.). This architecture isolates standing inventory capital from trailing velocity and future liabilities.

A. File 1: `inventory_snapshot.csv` (Mandatory)
The primary ledger of current capital allocation and pricing metrics.
- Relational Keys: `Item_Identifier`, `Item_Location`.
- Required Backend Fields: `Item_Description`, `Item_Type`, `Quantity_Available`, `Quantity_Committed`, `Unit_Average_Cost`, `Unit_Base_Price`, `Target_Stock_Level`, `Preferred_Vendor`, `Last_Sales_Date`, `Replacement_Item_Identifier`.
- Optional Fields (Coerced if missing): `UPC_Code`, `Manufacturer_Part_Number`, `Manufacturer_Brand`.

B. File 2: `annual_sold.csv` (Mandatory)
The trailing 365-day velocity engine. Separating this from the inventory snapshot significantly reduces the computational strain on the ERP's daily export query.
- Relational Keys: `Item_Identifier`, `Item_Location`.
- Required Backend Field: `Annual_Sold`.

C. File 3: `po_activity.csv` (Optional)
The future liability ledger. It tracks open capital commitments to calculate Open-To-Buy (OTB) cash collisions.
- Relational Keys: `PO_Number`, `Item_Identifier`.
- Required Backend Fields: `Date_Created`, `Order_Status`, `Purchase_Order_Vendor`, `Quantity_Ordered`, `Order_Total_Amount`.

4.2 POLARS SCHEMA INFERENCE & STRICT CASTING RULES
Polars is utilized over Pandas due to its multi-threaded Rust backend, strict type enforcement, and execution speed on 500,000+ row datasets. 

A. The Float64 Casting Mandate:
All quantities and financial metrics must execute as floating-point numbers to prevent integer truncation errors during margin analysis. Variables such as `Unit_Average_Cost` and `Quantity_Available` are explicitly cast to `pl.Float64`. Any nulls or entirely empty strings are strictly coerced to `fill_null(0.0)`.

B. The Utf8 (String) Sanitization Protocol:
All identifiers, locations, and descriptions are cast to `pl.Utf8`.
- Whitespace Contamination: ERPs routinely export trailing whitespace (e.g., "SKU-100   "). The parsing engine chains `.str.strip_chars()` to every string column to guarantee relational joins do not fail due to invisible characters.
- The Nested List Anomaly (`polars_list_compat.py`): In specific edge cases, Polars infers CSV cells containing commas as nested lists (`list[str]`) rather than scalar strings. A strict defensive function (`coerce_scalar_string_columns`) executes immediately upon ingestion, forcing any inferred list-like columns back to flat Utf8 strings to prevent catastrophic crashes during string concatenation.

C. Date Coercion:
Fields such as `Last_Sales_Date` and `Date_Created` are heavily subjected to ERP export drift. The engine utilizes `.str.strptime(pl.Date, format="%Y-%m-%d", strict=False)`. Unparseable or malformed dates are gracefully coerced to `null`, ensuring the pipeline continues executing while defaulting to high-risk aging assumptions for the affected rows.

4.3 PRE-FLIGHT VALIDATION & THE ROSETTA STONE UI
Because every WD customizes their ERP column headers (e.g., NetSuite’s `CustItem_QOH_Loc4` vs. standard `Quantity_Available`), Govnr employs a "Rosetta Stone" mapping interface in the Streamlit UI prior to activation.

A. The 50-Row Float/Date Sanity Check:
When an Admin maps a column, the Streamlit backend (`erp_mapping_validation.py`) extracts a 50-row non-null sample from that specific column. 
- Money Stripping: It programmatically strips `$`, `,`, and whitespace. 
- Type Assertion: If the mapped column (e.g., `Unit_Average_Cost`) contains unparseable strings (e.g., "TBD", "Discontinued"), the UI hard-halts and explicitly rejects the mapping, preventing the user from corrupting the daily automated pipeline.
- Duplication Prevention: The UI algorithm validates that no two backend variables are mapped to the same raw CSV column.

4.4 SCHEMA DRIFT & CHAOS PROTECTIONS
In Enterprise SaaS, clients will inevitably alter their ERP Saved Searches, rename columns, or accidentally delete outbound files. The ingestion engine is armored to handle these chaos vectors.

A. The `MissingFileError` Exception:
If the cron worker fails to locate `inventory_snapshot.csv` or `annual_sold.csv` in the SFTP drop zone, it halts execution, raises a `MissingFileError`, logs the failure to the database, and safely terminates the container. It does NOT process old data.
B. The `po_activity` Pruning Protocol:
Because Purchase Orders are an intraday variable, if the NetSuite system fails to upload a new `po_activity.csv`, Govnr explicitly deletes the stale local copy of the file before processing. If it did not do this, it would execute math against yesterday's POs, triggering false-positive Cash Collision warnings.
C. The `SchemaDriftError` Exception:
If the ERP system successfully drops the file, but the client altered the column headers (e.g., renaming "Average Cost" to "Avg Cost"), the mapped Rosetta Stone dictionary will fail to find the key. The engine triggers a `SchemaDriftError`, aborting the pipeline immediately to prevent generating a CFO report with a $0 Capital Deployed value.

5.0 EXECUTIVE SUMMARY
This volume codifies the mathematical core of the Govnr platform. The engine is not a passive analytics dashboard; it is a deterministic financial interceptor. Utilizing the Polars multi-threaded dataframe library, the engine applies strict, rules-based calculus to detect operational bleed, trapped capital, and impending cash flow collisions. The algorithms herein enforce institutional financial discipline upon chaotic, gut-driven wholesale procurement environments.

5.1 THE LOCATION-FIRST CALCULUS MANDATE
Traditional ERP reporting defaults to global inventory averaging. This is a catastrophic architectural flaw in wholesale distribution. A global average can show a "healthy" 60 days of supply for a SKU, masking the reality that Warehouse A has 0 units (losing daily sales) while Warehouse B has a 5-year supply gathering dust.
- The Govnr Standard: All financial calculus is executed strictly at the `[Item_Identifier, Item_Location]` row level. 
- Aggregation occurs only *after* location-level conditions are mathematically proven, ensuring absolute ledger accuracy per facility and exposing regional misallocations.

5.2 CAPITAL DEPLOYMENT & MARGIN INTEGRITY ALGORITHMS
These formulas baseline the total financial exposure and immediately flag pricing configurations that mathematically guarantee a loss.

A. Location Capital Deployed
- Formula: `Max(0.0, Quantity_Available + Quantity_Committed) * Unit_Average_Cost`
- Rationale: Committed stock has not yet been invoiced/shipped. It remains physical capital tied up on the warehouse floor. Total Capital Deployed is the absolute sum of this location-level metric.

B. Gross Profit Inversion (Selling at a Loss)
- Condition: `Unit_Average_Cost >= Unit_Base_Price` AND `Quantity_On_Hand > 0`.
- Action: Flags the SKU for immediate audit. Isolates items where the ERP pricing matrix has fallen behind vendor cost increases, causing the WD to actively subsidize their customers' purchases.

C. Missing / $0 Cost Basis
- Condition: `Unit_Average_Cost <= 0.00` AND `Quantity_On_Hand > 0`.
- Action: Quarantines the SKU. Without a deterministic cost basis, all margin analytics for that item are legally and mathematically invalid.

5.3 NON-PERFORMING CAPITAL (THE DEAD STOCK FORMULA)
The identification of Dead Stock must be aggressively protected against false positives. The "Harvester Bug" previously proved that blindly flagging items with `Annual_Sold == 0` inaccurately captures newly received inventory or recent warehouse transfers. 

A. The Deterministic Dead Stock Logic:
An item is exclusively flagged as Dead Stock if ALL of the following conditions are met:
1. `Quantity_On_Hand > 0`
2. `Annual_Sold == 0.0`
3. `Days_Since_Last_Sale > 365` (Enforces the aging requirement to protect fresh transfers).
4. `Replacement_Item_Identifier` is empty OR the designated replacement item's `Annual_Sold == 0.0`.

B. Supersession Awareness: In the automotive aftermarket, SKUs are frequently superseded by manufacturers. If the legacy part has 0 sales, but the *new* part has 500 sales, the legacy part is not "dead"—it simply needs its inventory merged or substituted. Condition 4 prevents Govnr from flagging healthy superseded capital as dead stock.

5.4 REGIONAL ARBITRAGE & WAREHOUSE TRANSFERS
Purchasing agents routinely buy new stock from external vendors to supply a starved warehouse, completely ignoring identical surplus stock sitting in a sister warehouse. Govnr identifies internal liquidity events to prevent external cash expenditure.

A. The Days Supply Metric:
- Formula: `Quantity_On_Hand / (Annual_Sold / 365.0)`. (If Daily Velocity is 0, Days Supply is capped at 999.0).

B. The Misallocation Trigger:
- Condition: For the exact same `Item_Identifier`, Location A exhibits `Days_Supply < 15` (Starved) AND Location B exhibits `Days_Supply > 180` (Bloated).

C. The Transfer Manifest Calculus:
Instead of blindly moving all inventory, the engine calculates the exact logistical requirement using the CFO's predefined `Target_Stock_Level`.
- `Surplus_Qty = Max(0.0, Quantity_Available - Target_Stock_Level)` at Location B.
- `Deficit_Qty = Max(0.0, Target_Stock_Level - Quantity_Available)` at Location A.
- `Transfer_Qty = Min(Surplus_Qty, Deficit_Qty)`.
- Action: Generates `Report_4_regional_disparity.csv`, explicitly routing the `Transfer_Qty` from the Source Warehouse to the Destination Warehouse.

D. Interbranch Cost Variance:
- Condition: `((Max_Unit_Cost - Min_Unit_Cost) / Min_Unit_Cost) > 0.25` across different locations for the exact same SKU.
- Action: Flags systemic accounting failures where freight or receiving errors have caused one warehouse to value an asset 25%+ higher than a sister warehouse.

5.5 THE CASH COLLISION ENGINE (ROLLING OPEN-TO-BUY)
This is the primary "Trojan Horse" value proposition. It functions as a temporal radar to intercept over-budget procurement before it impacts the cash conversion cycle.

A. Temporal Drift Protection: 
The engine NEVER uses `datetime.today()` to calculate the trailing window. It dynamically scans `po_activity.csv` and sets the `anchor_date` to the absolute maximum `Date_Created` present in the file. This ensures deterministic accuracy even if the Cron worker executes a day late.

B. The Exposure Calculus:
- The engine establishes a 7-day window: `[anchor_date - 7 days, anchor_date]`.
- It filters for lines where `Order_Status` IN `("Draft", "Pending Receipt")`.
- It calculates the absolute sum of `Order_Total_Amount` within that window.

C. The Intervention Trigger:
- If `Total_Draft_PO > weekly_otb_limit` (The CFO's locked configuration).
- Action: Calculates `Shortfall = Total_Draft_PO - weekly_otb_limit`. Triggers a RED Executive Dashboard alert and PDF directive instructing the CFO to block/cancel pending lines equal to the Shortfall.

5.6 THE SUPERSESSION PO BLOCK (PURCHASING INTERCEPT)
Buyers frequently memorize old part numbers. When an item is superseded, they order the new item while the legacy item still holds viable physical capital. 

- Condition: `po_activity.csv` contains a Draft or Pending PO for `Item_Identifier == Y`. The `inventory_snapshot.csv` contains `Item_Identifier == X`, where `X` has `Replacement_Item_Identifier == Y`.
- Execution Rule: If `Quantity_On_Hand` for `X` > 0, the engine physically flags the PO line for `Y`.
- Governor Action: "Replacement Item Alert: Recommended to deplete legacy Item_Identifier [X] before ordering replacement Item_Identifier [Y]."

5.7 ASSET PRODUCTIVITY (ABC & GMROI)
To segment the macro-health of the supply chain, the engine ranks the inventory ledger.
